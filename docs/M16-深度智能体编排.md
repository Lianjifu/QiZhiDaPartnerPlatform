# M16 · 深度智能体编排

> **模块 ID**：M16 · **路由**：`/copilot`（复用 M02 的会话入口） · **后端前缀**：`/api/copilot/*` · **实现度**：✅
> 导航：[← 索引](./README.md) · 上一模块 [M15 审计中心](./M15-审计中心.md) · 关联 [M02 专家协作](./M02-专家协作.md) · [M05 数字伙伴](./M05-数字伙伴.md)

**功能**：把 M02 的「对话 + 文本解析工具」升级为**能自主把活干完的数字伙伴编排**：结构化工具调用、上下文工程、按需派生子伙伴、人工审批后续跑、轨迹级回归评估。

本模块**不新增页面**：能力挂在 M02 专家协作的会话流与 M05 数字伙伴的档案/运行视图上。

## 2. 能力契约（Capability Contract）

### 2.1 数据模型

`internal/copilot/copilot_contracts.go:22`

```go
type CapabilityContract struct {
    Name        string         // 能力名(与 registeredTool.Name 一致)
    Kind        string         // builtin | tool | skill | workflow | platform
    Description string
    InputSchema map[string]any // JSON Schema 子集(type/properties/required)
    Mode        string         // execute | recommend | approval_required | prohibited
    Artifacts   []string       // 产物类型(docx/pptx/svg …)
    Approval    bool
}
```

契约表 `capabilityContracts`（`internal/copilot/copilot_contracts.go:95`）覆盖全部内置检索、受控 shell、渲染、Web/浏览器、MCP 与平台工具；技能与工作流用通用契约 `genericContract`（`internal/copilot/copilot_contracts.go:440`），动作原语固定为 `open|write|run|artifacts`。

### 2.2 三处受益

| 用途 | 落点 |
|---|---|
| 下发给模型的工具 schema | `registryToSchemas`（`internal/copilot/copilot_react_tools.go:34`） |
| 工具调用前的参数校验 | `ValidateContractArgs`（`internal/copilot/copilot_contracts.go:540`）→ 挂在 `authorizeToolCall`（`internal/copilot/copilot_tools.go`） |
| 伙伴详情页的能力视图 | `EmployeeCapabilityContracts`（`internal/copilot/copilot_contracts.go`）→ 伙伴载荷的 `capabilityContracts` 字段（`internal/server/employee_runtime.go`） |

### 2.3 校验失败不执行

参数不合法（缺必填 / 类型不符 / 枚举越界）时**不执行工具**，而是回一条结构化错误让模型自纠：

```
Permission: contract_invalid
Error: 工具参数不符合能力契约：参数 "command" 缺失(契约要求:shell.exec)
```

### 2.4 上岗闸门

拼写错误类的配置问题在**配置期**被拦下：`EmployeeContractIssues`（`internal/copilot/copilot_contracts.go`）用编辑距离比对已知契约名，命中即在 `validateEmployeeReleaseGates`（`internal/server/employee_validate.go`）拒绝上岗，错误码 `E_CAPABILITY_CONTRACT_MISSING`。

> 只拦平台内置命名族的疑似拼写错误；CMDB / 企业自带运行时工具有各自的执行器契约，不拦。

## 3. 结构化工具调用

### 3.1 协议层归一

`internal/modelprov/chat.go`

| 类型 | 位置 | 说明 |
|---|---|---|
| `ToolSchema` | `:20` | 下发给模型的工具契约 |
| `ToolCall` | `:30` | 模型发起的一次调用（`ID`/`Name`/`Arguments`） |
| `ToolResult` | `:37` | 工具执行结果回灌 |
| `ChatChunk.ToolCalls` | `:44` | 流式过程中还原出的工具调用 |

`buildChatBody`（`:301`）按协议拼装：

- **anthropic**：`tools:[{name,description,input_schema}]`；assistant 用 `tool_use` 内容块，user 用 `tool_result` 内容块
- **OpenAI 兼容 / ollama**：`tools:[{type:"function",function:{name,description,parameters}}]`；工具结果拆成 `role:"tool"` 的独立消息

流解析：`parseOpenAIStream`（`:542`）聚合 `delta.tool_calls[]` 片段，`parseAnthropicStream`（`:605`）聚合 `content_block_start` / `input_json_delta` / `content_block_stop`。

### 3.2 provider 不支持时的透明降级

`StreamChat`（`:132`）在服务端以 4xx 拒绝 `tools` 字段时，**自动去掉 tools 重发一次**（`errorsMentionTools` 判定）。此时不会有结构化调用，ReAct 继续走原有的文本解析路径 —— 两条路并存，不做硬切换。

### 3.3 轮内并行

`executeToolCalls`（`internal/copilot/copilot_react_tools.go:116`）在一轮内并行执行多个工具，**并发上限 4**（`reactToolConcurrency`）。

> 并行只影响吞吐：每个工具仍然走同一套授权闸 `DispatchAuthorizedToolFn`，边界策略不放松。

### 3.4 调用链

| 环节 | 位置 |
|---|---|
| 契约 → schema | `registryToSchemas`（`internal/copilot/copilot_react_tools.go:34`） |
| schema 下发 | `LLMCallOptions.Tools`（`internal/copilot/service.go`）→ `models.StreamLLMForCopilot`（`internal/models/handlers_stream.go`）→ `modelprov.Client.StreamChat` |
| 结构化调用 → 内部请求 | `structuredToolCalls`（`internal/copilot/copilot_react_tools.go:69`） |
| 执行 | `executeToolCalls`（`internal/copilot/copilot_react_tools.go:116`） |
| 回灌 | `toolCallsToResults`（`internal/copilot/copilot_react_tools.go:223`）→ `ChatMessage.ToolResults` |

## 4. 上下文工程

| 子项 | 阈值 / 口径 | 实现 |
|---|---|---|
| **会话压缩** | 历史 > 48 条时，把早期部分压成摘要，保留最近 24 条原文 | `CompactConversationHistory`（`internal/copilot/copilot_compact.go:38`），在 `internal/server/handlers_c.go:648` 调用 |
| **摘要生成** | 优先模型总结（≤300 字），失败退回确定性摘要 | `summarizeHistory`（`internal/copilot/copilot_compact.go:75`）· `fallbackHistoryDigest`（`:118`） |
| **上下文卸载** | 工具输出 > 4000 字时落 `agent_artifacts`，上下文只留引用 | `offloadToolOutput`（`internal/copilot/copilot_offload.go:45`） |
| **产物取回** | `artifact.read{id}` 工具按 id 取回全文 | `internal/copilot/copilot_tools.go`（builtin 分支）· `internal/server/agent_artifacts.go:35` |
| **提示缓存** | `CachePoints{0}` 标记 system 前缀 | `internal/modelprov/chat.go:301`（anthropic `cache_control`） |
| **待办回注** | 未完成待办注入下一轮 system prompt | `pendingTodosPrompt`（`internal/copilot/copilot_tools.go:444`）→ `internal/copilot/copilot_react.go:134` |
| **待办状态机** | `pending → in_progress → done`，按 id 迁移 | `internal/server/pilotdeck_tools.go`（`runtimeTodoWrite`） |

> 压缩**不删除任何原始消息**：摘要只是给模型看的更紧凑的视图，原始记录仍在会话里落库，可审计、可回放。压缩信息写进回合快照的 `compaction` 字段。

## 5. 自动升级（交接）

### 5.1 触发条件

伙伴在 `boundaryPolicy.handoff.triggers` 里声明升级条件（配置期由 `validateEmployeeConfigurationBody` 强制要求 triggers + approvers 成对出现），运行期由 `maybeEscalate`（`internal/copilot/copilot_escalate.go:83`）判定：

| 触发 | 判定点 |
|---|---|
| `prohibited_action` | 工具被边界策略拒绝（`Permission == "prohibited"`） |
| `tool_failure` | 同一工具连续失败 ≥ 2 次（`escalateFailureThreshold`） |
| `user_request` | 用户显式要求转人工 |
| `boundary_exceeded` | 请求超出岗位职责边界 |

**未配置 handoff 的伙伴永不自动升级**（默认关闭，避免打断正常工作）。

### 5.2 交接动作

`internal/server/escalation.go:66` `escalateDigitalPartner`：

1. 定位会话（幂等：已在接管中则不重复移交）
2. 接管人取伙伴的 `escalationOwner`（上岗闸门强制必填），用 `resolveApproverCandidatesLocked` 解析成工作区成员；未配置则回落 `handoff.approvers[0]`
3. 写 `sess["handoff"] = {active, ownerId, ownerName, note, at}`
4. 写审计「自动升级交接」→ `runtime.handoffs24h` 由此**真实计数**（此前是从审计里 grep「交接」）
5. 会话进入接管态后写操作被 `assertSessionWritableLocked` 拦截（`E_SESSION_HANDOFF`）

## 7. 人机共岗（审批后续跑）

### 7.1 挂起

工具命中 `approval_required` 时：

1. 平台把调用挂进审批队列（既有 `queueToolAuthorization`，`internal/server/authorization_queue.go`），待审单 ID 随 `toolExecResult.ActionID` 返回
2. ReAct 循环检测到 `pending_authorization` → **本回合以 `awaiting` 结束**（`internal/copilot/copilot_react.go:306`、`:326`），SSE 发出 `awaiting` 事件
3. 最终文本明确「已进入人工审核队列，等待授权通过后将继续执行」——**不宣称已执行**

### 7.2 续跑

`POST /api/copilot/conversations/{cid}/turns/{corr}/resume`（`internal/server/copilot_resume.go:17`）

| 环节 | 位置 |
|---|---|
| 路由 | `internal/server/server.go`（`/resume` 分支） |
| 收集已决策动作 | `pendingActionsForCorrelationLocked`（`internal/server/copilot_resume.go:124`） |
| 执行已批准工具 | `ResumeTurn`（`internal/copilot/copilot_resume.go:74`）→ `runCopilotTool` |
| 驳回理由回喂 | 同上（拒绝时把理由作为观察喂回模型） |
| 续跑模型回合 | 同上 → `runReactTurn`（带着审批结果的观察） |
| 落回会话 | `persistResumedTurn`（`internal/server/copilot_resume.go:171`） |

SSE 事件序列：`stage(resume)` → `tool` → `delta` → （如再次触发审批）`awaiting` → `done`。

> SSE 协议只增不改：新增 `awaiting` 事件类型，旧前端忽略未知事件即可。

## 8. 轨迹评估

### 8.1 轨迹格式

`internal/copilot/trajectory/trajectory.go`

```go
type Trajectory struct {
    ConversationID, CorrelationID, DigitalPartnerID, ModelID string
    Steps           []Step   // {Seq, Tool, Args, Status, DurationMs, Permission}
    FinalText       string
    Tokens          int
    TerminatedBy    string   // final | max_steps | budget | cancelled | awaiting
}
```

来源全部是既有落库记录（助手消息上的 `toolCalls` + 回合状态），不新增采集通道。装配入口 `BuildTrajectoryFromMessages`（`internal/copilot/copilot_trajectory.go:11`）。

### 8.2 断言器

| 断言 | 用途 |
|---|---|
| `ExpectTool` / `ExpectNoTool` | 调过 / 没调过某能力 |
| `ExpectToolBefore` | 两个能力的先后顺序 |
| `ExpectArgs(tool,key).Contains(sub)` | 参数子串 |
| `ExpectToolCount(t).AtMost(n)` / `ExpectMinToolCount(t).AtLeast(n)` | 调用次数 |
| `ExpectTerminateWithin(n)` | 步数上限 |
| `ExpectTerminatedBy(reason)` | 终止原因（含 `awaiting`） |
| `ExpectFinalContains(sub)` | 最终回答内容 |
| `ExpectEscalated()` | 发生过人工升级 |

### 8.3 用例库

`internal/copilot/trajectory_fixtures_test.go` 用脚本化模型应答驱动**真实的 ReAct 循环**，覆盖 7 类岗位剧本：直答、单工具、多步顺序、单轮并行、工具失败、审批挂起、观察是否真的进入下一轮。

### 8.4 上岗评测改用真实轨迹

`internal/server/employee_trajectory.go:18` `computeEmployeeTrajectorySummaryLocked`：

```
score = 100 − 15×工具失败 − 10×挂起审批 − 20×越界 − 1×超长路径
```

- 通过线 85（`employeeTrajectoryPassScore`）
- `evaluation.trajectory` 落 `{status, score, turns, toolCalls, failures, awaiting, escalations, violations}`
- 伙伴载荷的 `trajectory` 字段同步投影，供详情页展示
- **没有任何真实回合时 `status=unknown`**：不给假分数，保留结构性评测

> 此前 `evaluate` 写死 `score: 93.5 / 68.0`，现已改为真实轨迹评分。

## 8.5 前端交互约定

| 场景 | 用户看到什么 |
|---|---|
| 工具命中人工授权 | 授权卡上出现「本回合已挂起：工具「X」等待人工授权，授权通过后可续跑同一个回合」；模型**不会**宣称已执行 |
| 审批人驳回 | 授权卡显示「已拒绝」；驳回理由会在续跑时作为观察喂回模型，由它决定下一步 |
| 审批通过 | 授权卡出现「继续执行」按钮 → 调用 resume → 后端真实执行被批准的工具 → 结果作为一条新助手消息追加到会话 |
| 尚未决策就点续跑 | 后端返回 404「该回合没有待续跑的审批动作」，前端原样提示 |
| 伙伴没有真实回合 | 「运行观测」显示「暂无运行轨迹」，不给任何编造分数 |

## 8.6 回复内容格式与「不泄底」约束

用户气泡里原本直接渲染了后端的内部推理叙述（`step.detail`），回复读起来像日志：
`理解任务：…` / `模式 deep · default_logic` / `client_hint` / `retrieve` / `第 1/5 步：…` / `结论 → 关键依据 → 下一步`。
现在内部叙述与用户可见正文彻底分离。

### 前端：推理细节不再进正文

| 位置 | 改法 |
|---|---|
| `CopilotPage.BubbleSplitter.ts` `extractThought` | reasoningSteps 只作为**结构化数据**返回，**不再**把 `step.detail` 拼成正文 |
| 同上 `splitMessageIntoBubbles` | thought 片段 `content` 置空；叙述文本改挂 `thinking` 字段，由 `TurnThoughtPanel` 折叠展示 |
| `CopilotPage.MessageBubble.tsx` | 用户气泡改用当前登录人身份（此前硬编码「王昊」）；助手头部拆成「身份（左）/ 状态·时间·审计（右）」两段 |
| `CopilotPage.ToolCallRow.tsx` + `lib/human-tool-name.ts` | 工具调用卡片显示「知识检索 / 记忆回忆 / 受控命令」等能力名；原始标识保留在展开明细里 |

> 结论：`TurnThoughtPanel` 本来就把 reasoningSteps 按「意图理解 / 任务规划 / 工具执行 / 质量复核」四阶段分组渲染，
> 正文再抄一遍是纯冗余，且把内部代号泄给了用户。

### 后端：内部代号一律翻译成人话

| 位置 | 改法 |
|---|---|
| `copilot_thought.go` `humanRouteReason` | `client_hint` → 「按指定模式处理」；未知 reason 一律回落通用文案，**不再原样透出** |
| `copilot_thought.go` `humanToolName` | `knowledge.retrieve` → 「知识检索」、`memory.recall` → 「记忆回忆」、`shell.exec` → 「受控命令」… |
| `copilot_thought.go` `thoughtForToolChoice` | 工具选择理由不再把工具名当 detail（此前是 `knowledge.retrieve`） |
| `copilot_cognitive.go` `cognitiveModeLabel` / `humanCognitiveReasons` | `deep` → 「深度」；`default_logic` / `signal:logic` / `dept_pref:creative` → 「默认逻辑框架」/「识别到逻辑思考分析特征」/「部门偏好创意决策分析」 |
| `copilot_plan.go` `humanPlanAction` | 计划步骤 action `retrieve`/`memory`/`tool`/`answer` → 「检索知识」/「回忆偏好」/「调用能力」/「整理结论」 |

### 答复正文：结论先行，纯段落无标题

`copilot_plan.go` 的汇总器 prompt 要求模型按固定骨架作答，但**不写 Markdown 标题**：

```
先写结论段（1–3 句，直接回答用户的问题，先给结论再给理由）
再写依据段（每条一行；来源用「知识库」「跨会话记忆」等自然说法，不写工具技术名）
最后写下一步段（可执行动作：负责人/期限/步骤，没有明确下一步时省略）
三段之间空一行；不要使用 Markdown 标题
```

页面不做视觉分区：模型仍按「结论 → 依据 → 下一步」的顺序组织内容，读者靠语序而非小标题分辨。

> 内部代号只允许出现在**机器可读**的遥测里（route 事件的 `reason`、`cognitive.reasons` 快照），这些字段前端不渲染。

### 消息流：拍平成 Claude Code 风格

协作页原先把每条消息渲染成带边框的卡片（助手气泡 `border + surface-1 + shadow + radius16`、
每个工具调用一个满宽橙底卡片、思考面板一个独立卡片），视觉噪声大。现在消息流改为「正文直接排在页面背景上 + 少量灰色折叠组」。

| 元素 | 改法 |
|---|---|
| 助手 / 工具气泡 | `global.css` 去掉 `border` / `background` / `box-shadow` / `padding` / `border-radius`；hover 不再描边 |
| 工具调用 | `BubbleSplitter` 把全部 `toolCalls` 合并成**一个** `tool_call` slice；`CopilotPage.ToolCallGroup.tsx` 渲染成「调用了 N 项能力 ›」折叠条，展开后是浅灰圆角盒，盒内每项能力一行（复用 `ToolCallRow`）。流式期间自动展开，结束后自动收起（用户手动展开过则不再自动接管） |
| 思考面板 | `turn-thought-panel.tsx` 收起态去掉卡片边框与底色，改为淡灰文本行；展开态用左侧竖线分组，不用横向分隔线 |
| 用户气泡 | 底色由品牌紫 `bg-[var(--brand-light)]` 改为中性灰 `bg-[var(--surface-3)]`，去掉描边与阴影；身份行（时间 / 姓名 / 头像）从气泡**上方**移到**下方**的操作行，与 Claude Code 一致 |
| 跨回合留白 | 卡片移除后原先靠卡片 padding 形成的留白消失，改由 `CopilotPage.Messages.tsx` 外层容器 `gap-6` 承担；同回合内 `.bubble-stack` 维持 `gap-2` |
| 答复正文 | 模型自发的 `##` / `###` 退化为与正文同号的强调行（无字号跳变、无品牌竖条），答复不再做视觉分区 |
| 会话列表预览 | 预览来自答复正文，去掉 Markdown 标题标记（`## 结论` → `结论`），列表里不出现裸标记（后端 `StripMarkdownHeadingMarkers` 写入时去，前端渲染时再去一次以覆盖历史会话） |

三栏布局、思考面板、回放 / 审计 / 能力调用数 / 写操作徽标等治理与可观测入口一律保留，只是从卡片头挪到更淡的位置。

### 答复正文：Markdown 全量

原先协作页答复正文走的是一份自研的轻量 Markdown 渲染器，只支持标题 / 粗斜体 / 行内代码 / 单层列表 / 引用 / 表格 / 代码块——嵌套列表会拍平、任务列表、删除线、脚注、图片都不认，表格单元里的 `|` 还会切错列。
现在换成 **markdown-it**（CommonMark + GFM 全量）：

| 能力 | 说明 |
|---|---|
| 结构 | 标题 1–6 级、段落、有序 / 无序列表（**任意嵌套**）、任务列表（`- [x]` 渲染成真实 checkbox）、引用块（多行合并）、分割线 |
| 行内 | 粗体、斜体、删除线、行内代码、链接、图片、自动链接（裸 URL） |
| 块级 | GFM 表格（`\|` 转义、`:---:` 对齐）、围栏代码块（按语言高亮，带语言 class） |
| 扩展 | 脚注（`[^1]`；脚注 id 按消息加前缀，避免页内多条消息的 id 冲突） |
| 保留的本地约定 | 下划线填空（`____` → 可视空格 `md-blank`）、表单抬头行（`部门：___  整理人：___` → `md-form-meta`） |

安全：markdown-it 以 `html: false` 运行，**原始 HTML 一律转义**（不会形成 XSS）；链接 URL 走 markdown-it 自带的 `validateLink`，`javascript:` 等协议不生成 `href`。回归锁在 `src/components/Markdown.full.test.ts`。

渲染出的类名沿用既有约定（`md-content` 下的 `md-*`），`global.css` 不必重写；新增 `md-img` / `md-del` / 任务列表 / 脚注的样式。顺带修掉一个老问题：Tailwind preflight 把 `ol/ul` 的 `list-style` 清成了 `none`，列表一直没有圆点和序号，现已显式恢复。

### 消息流阅读列与响应式

宽屏下正文贴着消息区左边缘、右侧留一大片空白，输入框却又是居中的（`max-w-3xl`），三者互不对齐。现在正文 / 输入框 / 头部内容共用**同一个阅读列**并居中：

- `global.css` 新增 `.copilot-column`（`width:100%; max-width:var(--copilot-reading-w); margin-inline:auto`）与 `--copilot-reading-w`（默认 880px，≥1800px 放宽到 960px）。
- 应用点：消息流容器、输入框内层、头部内容、告警条、空状态。
- 助手气泡正文去掉原来的 `max-w-[800px]`，改由阅读列统一控制，头部的「时间 / 回放 / 审计」也就落在正文右边缘，不再悬在半空。
- 移动端：`AppLayout` 的外壳网格补上 `grid-cols-[minmax(0,1fr)]`——此前顶栏用 `col-span-2` 在移动端撑出了第二列，顶栏只占半屏、右边露一条空白；同时补 `minmax(0,1fr)` 防止内容把网格撑破。代码块桌面横向滚动、移动端折行，表格横向滚动。

## 10. 边界

- **provider 能力**：原生 `tool_use` 需要模型侧支持；不支持时透明降级为文本解析路径（行为与改造前一致）
- **Cap 侧车链路**：`/api/model-invoke/stream` 目前不透传结构化工具调用，collab 模式下退回文本解析
- **子伙伴**：只做**一轮**子任务（`delegationChildMaxSteps = 4`），不做多轮嵌套；不跨伙伴（除非配了 `allowedTargets`）
- **续跑**：审批通过后执行的是**被批准的那一次调用**，不是重放整段会话；模型侧接着往下走的是新一轮 ReAct
- **轨迹评分是启发式**：基于失败/挂起/越界计数，不是模型质量评分
- **治理层未削弱**：`capabilityModes` 四档、SoD/双签、动态零信任、沙箱白名单、审计留痕全部保持原语义
