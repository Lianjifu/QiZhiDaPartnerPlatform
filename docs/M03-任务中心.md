## 边界

- **锁契约（易踩坑）**：`transition` 把任务推到 `review` / `completed` 时，`taskRoute`（`internal/tasks/handlers_route.go:35` 已持 `Store.Lock()`）会调 `writeTaskWorkingMemoryLocked`（`internal/tasks/handlers_memory.go:19`）→ `Deps.IngestRuntimeMemoryLocked` → `server.ingestRuntimeMemoryLocked`（`internal/server/server.go:2207`）→ `memory.Service.IngestRuntimeMemoryLocked`（`internal/memory/service.go:236`）。该方法**不取锁**（调用方已持锁，`Store.mu` 是不可重入的 `sync.RWMutex`）；同包的 `IngestRuntimeMemory`（`:225`）才是自带 `Store.Lock()` 的变体，二者不可混用——历史上曾把此处误接成加锁版，导致 `running → completed` 请求自锁死并连带阻塞全后端（回归于 `4f6b588`，已修复）
- `auditor` 只读核查，不参与执行（`roleCanMutate`）——但任务审批需 admin，普通 user 无法自批
- 定时作业的 `run` 是**同步建单**，实际执行由后续 worker 消费 `Store.Tasks`
- 任务变更后是 `go Store.Persist(...)`（异步），不等待落库完成
