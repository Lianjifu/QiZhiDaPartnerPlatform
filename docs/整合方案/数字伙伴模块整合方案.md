## 一、背景与目标

### 1.1 背景

M05 数字伙伴(系统亦称 Digital Partner / de-office)是平台"角色化"的载体:可发布、可审批、可暂停、可接入工作流。包含数字员工管理、模板采纳、能力目录、配置版本审批等子功能。

代码当前形态:

- **前端**:`pages/Partners.tsx` 单文件 **2510L**(6.3× 超 400L TSX 门禁,**必须拆**);`lib/partners.ts` 513L;`components/PartnerAvatar.tsx` 117L;**无 `features/partners/` 目录**
- **后端**:`backend/internal/server/` 中**混合文件**(M03+M05 混居):
  - `handlers_contract.go` **1145L**(L29-249 = M03 task handlers;L297-674 = M05 partner handlers)
  - `handlers_b.go` 411L(M05 partner handlers)
  - `handlers_capability_catalog.go` 596L(M05 能力目录,临界 ≤600L)
  - `connect_services.go` L49:`partnerv1connect.NewPartnerServiceHandler(&partnerConnect{s})` binding
- **微服务**:无现成脚手架;`qzda-partners` 保留命名但未创建

`internal/server/server.go` 中 M05 路由 **11 条**(L667-L705):
1. `GET /api/partners` → `s.listEmployees`
2. `POST /api/partners` → `s.createEmployee`
3. `GET /api/partners/overview` → `s.employeeOverview`
4. `GET /api/partner-templates` → `s.listEmployeeTemplates`
5. `POST /api/partner-templates` → `s.listEmployeeTemplates`(alias)
6. `GET /api/partner-template-adoptions` → `s.listTemplateAdoptions`
7. `GET /api/partner-capability-catalog` → `s.capabilityCatalog`
8. `POST /api/partner-templates/:id/adopt` → `s.adoptTemplate`
9. `PATCH /api/partner-templates/:id` → `s.listEmployeeTemplates`
10. `/api/partners/:id/*`(GET/POST/PATCH,含 12 子 action:`evidence`/`runtime`/`configuration-versions[/:id/approve]`/`configuration`/`evaluate`/`release/{withdraw,reject}`/`lifecycle`/`submit`/`approve`/`reject`/`pause`)→ `s.digitalEmployeeRoute`
11. `GET /api/agents` → `s.legacyAgentsProxy`

### 1.2 目标

- **前端**:`grep frontend/web/src/features/partners/` 找全所有 M05 代码;PartnersPage ≤400L(shell),tab 子组件 ≤400L
- **后端**:`grep backend/internal/partners/` 找全所有 M05 handler + 业务 + capability + connect
- **行为零变化**:employee lifecycle、模板采纳、能力目录、配置版本审批链(submit→approve/reject/pause)、Connect-RPC 兼容全部保留
- **包边界真实**:`internal/partners/` 自包含,只依赖 `internal/auth`、`internal/policy`、`internal/store`、`pkg/errors`
- **拆 handlers_contract.go**:M03 部分(L29-249)→ `internal/tasks/` 收尾;M05 部分(L297-674)→ `internal/partners/`

## 五、Gap 与风险

### G1 · `handlers_contract.go` 1145L 跨模块拆分

同文件含 M03 task routes L29-249 + M05 partner routes L297-674。

**Why:** 同文件并发路由,无法独立迁移
**How:** P2 先 diff 确认 L29-249 + L687-704 属 M03(若是,迁 `internal/tasks/`;M03 P2 完成后 L687-704 兜底代码可能已成 dead code,可同步删除)。M05 主体 L252-674 迁 `internal/partners/`。

### G2 · `digitalEmployeeRoute` 12 子 action 单文件上限

`handlers.go` ≤400L gate 临界。

**Why:** 12 个子 action 集中在 `digitalEmployeeRoute` 一个方法,代码量大
**How:** `handlers.go` (~400L,主路由 + 多数子 action) + `handlers_actions.go` (~400L,审批类子 action `submit`/`approve`/`reject`/`pause`/`release/{withdraw,reject}`)。或再细切 handlers_evidence.go / handlers_configuration.go / handlers_lifecycle.go

### G3 · Connect-RPC binding 跟迁

`partnerv1connect.NewPartnerServiceHandler(&partnerConnect{s})` 在 `connect_services.go` L49。Connect binding 需 server 实例 → 需传 Service struct 到 connect handler。

**Why:** Connect-RPC 是另一个 HTTP 入口,跟 REST 路由并行
**How:** `connect.go` 中 `new()` 接收 Service,connect 注入 service 实例。`server.go` 初始化时同步创建 partnerConnect。

### G4 · M02 → M05 跨模块入口

copilot 选员工/列员工/调员工概览走 M05 路由。迁完后 copilot 调用 `s.partnerSvc.ListEmployees`。

**Why:** 跨模块包依赖需 decoupling
**How:** P2 deep-move 后,`internal/copilot/` 中通过 Deps 注入 `ListEmployees` 函数值。同 M03 P2 模式。

### G5 · 拆分后 `digitalEmployeeRoute` 与 `listEmployeeTemplates` 别名路由

`POST /api/partner-templates` 与 `PATCH /api/partner-templates/:id` 都调用 `s.listEmployeeTemplates`(alias)。迁完后 alias 仍要保留。

**Why:** RESTful 兼容性
**How:** `server.go` L673-L683 注册时同一 handler,迁完不变。
