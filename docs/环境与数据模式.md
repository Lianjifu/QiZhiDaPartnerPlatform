# 环境与数据模式：dev / pro

## 三套环境

前端 `VITE_API_MODE` 与后端 `QZDA_MODE` 组合决定环境：

| 环境 | 前端 `VITE_API_MODE` | 后端 `QZDA_MODE` | 后端 | 说明 |
|---|---|---|---|---|
| **生产** | `api` | `pro` | 需要（PG；OIDC 可选） | 双人审批，禁 mock 身份与 mock token；登录为真实账号（哈希密码）或企业 OIDC；供应商凭据 AES-256-GCM 加密后存库（`QZDA_CREDENTIAL_KEY`），配置 Vault 时优先写入 Vault |
| **开发** | `api` | `dev` | 需要（PG，可选内存） | 本机联调，允许 mock 身份与 mock token |
| **演示** | `demo` | 不需要 | 无 | 浏览器内 mock，不请求任何后端 |

生产环境账号登录：账号存放在 `platform.auth_accounts`（迁移 `0006_auth_accounts.sql`），密码以 PBKDF2-SHA256 哈希保存。用命令行管理（密码从 stdin 读取，不出现在命令行参数里）：

```bash
printf '%s\n' "$PASSWORD" | QZDA_DATABASE_URL=... go run ./cmd/qzda-account add --email admin@corp.example --role admin --name "平台管理员"
printf '%s\n' "$PASSWORD" | QZDA_DATABASE_URL=... go run ./cmd/qzda-account set-password --email admin@corp.example
QZDA_DATABASE_URL=... go run ./cmd/qzda-account disable --email admin@corp.example
```

生产环境登录也可走企业 OIDC：后端需配置 `QZDA_OIDC_ISSUER`、`QZDA_OIDC_CLIENT_ID`、`QZDA_OIDC_CLIENT_SECRET`。`QZDA_OIDC_REDIRECT_URL` 默认 `http://127.0.0.1:8010/login/oidc/callback`（本地前端地址，无需公网），需在 IdP 登记同一地址。登录页的「企业账号登录（OIDC）」按钮跳转 IdP，回调页用 `code`/`state` 换取令牌；演示环境不显示该按钮。

启动：

```bash
# 开发：后端 dev + 前端 api
cd backend && make run-dev
cd frontend/web && npm run dev

# 演示：仅前端，无后端
cd frontend/web && npm run dev:demo

# 生产：后端 pro（前端构建时 VITE_API_MODE=api，为默认值）
QZDA_MODE=pro docker compose -f backend/deploy/compose.yml up -d
```

## 后端总开关

`QZDA_MODE` = `dev` | `pro`，默认 `dev`。任何非 `dev` 的值按 `pro` 处理（fail-closed）。

| `QZDA_MODE` | 数据 | 身份与登录 | 双人审批 / Vault | 内置对话 / runtime stub | Skill 签名 | 开发签名密钥 |
|---|---|---|---|---|---|---|
| `dev`（默认） | PG；`QZDA_DATA_BACKEND=memory` 时改为内存 + ACME seed，不写 PG | 允许 `x-mock-*` 身份头与 mock token；允许密码登录 | 关 | 开 | 信任任一已知 key | 自动生成 |
| `pro` | 必须 PG（忽略 `QZDA_DATA_BACKEND`） | 禁 `x-mock-*` 与 mock token；密码登录须通过 `platform.auth_accounts` 校验，OIDC 可用 | 开 / 必需 | 关 | 必须工作区 key | 不生成 |

`QZDA_DATA_BACKEND` 只影响 dev：`pg`（默认）或 `memory`。模式相关的单项覆盖开关（如 `QZDA_BAN_MOCK_TOKEN`、`QZDA_ALLOW_MOCK_IDENTITY`、`QZDA_FORCE_OIDC`、`QZDA_EMBEDDED_CHAT`）已全部移除，行为完全由 `QZDA_MODE` 决定。

本机 LaunchAgent（`scripts/dev-stack/run-stack.sh`）默认 `QZDA_MODE=dev`，PG 持久化。

## 前端 API 模式

`VITE_API_MODE` = `api` | `demo`，默认 `api`。其他值会在应用启动时报错。

| `VITE_API_MODE` | 请求去向 | mock 代码 |
|---|---|---|
| `api`（默认） | 真实网关（同源 `/api` → Vite proxy → `:8089`） | 不打包 |
| `demo` | 浏览器内 mock handler，不请求后端 | 动态加载 |

## Postgres 只使用 Docker

本机联调 **禁止** 再跑 Homebrew / 本机 Postgres。`QZDA_DATABASE_URL` 的 `127.0.0.1:5432` 必须指向 Compose 服务 `qzda-postgres`（镜像 `postgres:16-alpine`）。

若本机曾安装 `postgresql@17` 等并监听 `127.0.0.1:5432`，会抢掉 Colima 端口映射，导致 qzda-app 连到错误的库。启动前执行：

```bash
bash scripts/dev-stack/ensure-docker-postgres.sh
# 或
cd backend && make infra-env
```

脚本会停掉占用 5432 的 Homebrew Postgres，拉起 `qzda-postgres`，并校验版本为 16.x。

## 空库不再灌演示 seed

`apprun` 在 PG 持久化模式下使用 `store.NewEmpty()`，**禁止**「空库 PersistNow(seed)」。启动时仅：

- hydrate 已有 PG 行
- **确保稳定壳工作区 `w1`（名称「默认工作区」）存在**：即使库里已有用户自建工作区（如 `workspace-1`），仍会补齐 `w1`；并按 owner/成员重建内存访问授权，避免重启后列表被 JWT 固定 `w1–w4` 滤空
- 确保 builtin 技能目录 + **各工作区** `autoInstall` 岗位包（含 `general` / `office`）（`EnsureBuiltinSkillsReady`）
- 确保办公开箱知识包 published（`EnsureBuiltinKnowledgeReady`）
- 确保出厂流程模板（办公 Certified + 部门审批 + 高级库）（`EnsureBuiltinWorkflowsReady`）；个人模板 `wft-user-*` 不覆盖
- 内存存储（`QZDA_MODE=dev QZDA_DATA_BACKEND=memory`）时补通用员工；办公助手 `de-office` 随通用伙伴路径写入

### 硬删除必须 PersistDelete

多数集合是 **Upsert**，只改内存切片再 `Persist` **不会**删掉 PG 旧行。会话/知识/模型供应商/渠道部署/技能卸载/个人流程模板（`workflow_templates`）等硬删路径需调用 `PersistDelete` / `PersistDeleteSync`（kernel 表走 `KernelStore.DeleteMany`）。记忆记录当前为软删（`status=revoked`）。

环缓冲裁剪（`context_snapshots`、`channel_inbound`）亦需对被挤出 id 调删除。

### 工作区 Header 不可伪造

`x-workspace-id` 只能在身份已绑定成员集合内选择；显式传入未授权工作区返回 **403** `E_WORKSPACE_SCOPE`（空 Header 则回落默认/首选工作区）。三层作用域目标模型见 [ADR-014](./adr/ADR-014-scope-layers.md)。

### 为何联调时仍看到「演示 + 生产」混在一起？

常见误判有两类：

1. **Network 里同一接口出现两次**  
   React `StrictMode`（开发态）会故意双挂载，导致 `useApiQuery` 打两遍**同一个**真实网关。这不是「演示接口 + 生产接口」两套来源。前端 `VITE_API_MODE=api`（默认）时只会走 gateway。

2. **单个接口响应里既有 ACME seed 又有真实数据**  
   历史版本曾用 `NewDemo()` + Persist 把演示数据写进 Postgres。切到 `dev`（PG）后只是不再**新灌** seed，但 **hydrate 会把库里已有行全部读回**。

清理残留（含联调会话/记忆等第二阶段清空；保留模型供应商与工作区壳）：

```bash
psql "$QZDA_DATABASE_URL" -f backend/scripts/purge-demo-seed-ids.sql
# 或 make db-reset-dev（危险：丢全部数据）
cd backend && make build
launchctl kickstart -k "gui/$(id -u)/com.qizhida.dev-stack"
```

## 审批（上架 / 上岗 / 发布）

| 角色 | 行为 |
|------|------|
| **管理员** | 申请可直接生效，可自批；高风险也可跳过会签 |
| **普通用户** | 须审批；申请人不可自批；高风险需管理员首批 + 另一管理员会签 |

覆盖：上岗、路由、知识、流程技能、技能目录晋升、备份等（见 `dual_approval.go`）。

## 技能岗位包与平台工具

| 概念 | 说明 |
|------|------|
| **平台工具** | `manifest.platformTools`（如 `knowledge.retrieve`）；Go Harness **内置**，冷启动即用，**无需岗位包安装** |
| **通用岗位包** | 冷启动自动装到各工作区（weather / docx / …） |
| **办公岗位包** | 冷启动自动装 `office`（summarize/docx/pdf/pptx/spreadsheets/diagram-maker） |
| **协作扩展 / 重依赖 / 全量** | 按需 `POST /api/skills/apply-pack/:id` 装到**当前工作区**；重依赖须审批单号 |

`GET /api/skills/packs` 按工作区返回 `installed` / `installedCount` / `missingSkills`，并附带 `platformTools` 清单。前端「平台工具 → 岗位包」据此显示「已安装」而非仅 toast。

| 资产 | 路径 | 说明 |
|------|------|------|
| 知识包 | `backend/builtin/knowledge/office/` | `kp.{hr,admin,sales,market}.*` 共 10 包（人事3 / 行政4 / 销售2 / 市场1），冷启动写入并 published |

- **平台内置 / 个人创建** 分栏；个人模板支持存为模板与删除（`wft-user-*`）
