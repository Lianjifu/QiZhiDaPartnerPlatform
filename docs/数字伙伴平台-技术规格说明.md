## 0. 文档使用说明

### 0.1 每组件的 5 段统一描述模板

本规范中所有组件都按以下 5 段标准格式编写：

| 段 | 含义 | 内容 |
|---|---|---|
| **选型理由** | 选它的"原则依据" | 哪个 12 项原则触发了这个选择 |
| **与谁对比** | 同领域 2-3 个替代方案 | 用表格对比关键差异 |
| **核心优势** | 选中的相对备选强在哪 | 可量化的指标 + 业务影响 |
| **完成什么** | 在我们平台具体支撑哪些功能 | M01–M15（或 L2 横切能力）中哪些用到了 |
| **故障案例 / 教训** | 历史教训 | 有则必写，影响决策 |

## 2. 选型原则与决策框架

### 2.1 12 项强制原则

| # | 原则 | 说明 | 触发否决条件 |
|---|---|---|---|
| 1 | **生命周期 ≥ 5 年** | 选型必须有 5 年以上保证 | 社区 fork 数 ≤ 100/年 |
| 2 | **国产替代** | 必须有可投产的国产备份 | 没有信创方案 |
| 3 | **等保 3 + ISO 27001** | 必须支持合规测评 | 不能过 94 项检查 |
| 4 | **信创兼容** | 必须支持国产芯片/操作系统 | 不可运行华为云 / 海光 |
| 5 | **5 年内不会重构** | 不能列入"未来重写"清单 | 团队无学习路径 |
| 6 | **退出成本 ≤ 6 月** | 替换时不超过 6 月 | 数据迁移 > 6 月 |
| 7 | **团队能维护** | 团队有学习路径 | 需要招人 |
| 8 | **月费用稳定** | 不随用量非线性增长 | 阶梯式收费 |
| 9 | **社区活跃** | 5 年内 fork 数 ≥ 1000 | 维护停滞 |
| 10 | **文档完整** | 官方文档覆盖率 ≥ 80% | 文档不全 |
| 11 | **漏洞响应 ≤ 7 天** | 安全补丁及时 | CVE 长期未修 |
| 12 | **可观测** | 必须支持 OpenTelemetry | 不可插桩 |

### 2.2 决策评分卡（100 分制）

| 维度 | 权重 | 评分标准 |
|---|---|---|
| 5 年生命周期 | 20% | 低 = 0, 中 = 5, 高 = 10 |
| 国产替代就绪 | 15% | 无 = 0, 部分 = 5, 完全 = 10 |
| 等保 3 / ISO | 15% | 无 = 0, 部分 = 5, 全支持 = 10 |
| 性能匹配业务 | 15% | 不达标 = 0, 达标 = 5, 超标 = 10 |
| 团队能力 | 10% | 需大培训 = 0, 中等 = 5, 即学即用 = 10 |
| 社区文档 | 10% | 文档不全 = 0, 中等 = 5, 完整 = 10 |
| 成本可控 | 10% | 不可控 = 0, 中等 = 5, 稳定 = 10 |
| 退出成本 | 5% | ≥ 12 月 = 0, 6-12 月 = 5, ≤ 6 月 = 10 |

**通过：** 总分 ≥ 80 分；任一"5 年寿命"维度 < 5 分 → **直接否决**。

### 2.3 不可变清单（违反需走 ADR）

- ❌ 不能换 K8s 为 Swarm / Mesos
- ❌ 不能把 PostgreSQL 换为 MySQL / MongoDB
- ❌ 不能换 OpenSearch 为 Elasticsearch v8（许可证风险）
- ❌ 不能用虚拟机替代容器
- ❌ 不能去掉 OpenTelemetry
- ❌ 不能去掉 gVisor 沙箱
- ❌ 不能去掉 Prometheus + Grafana
- ❌ **不能"业务用 Python"或"AI 用 Go" 跨界**（双栈各司其职）
- ❌ **不能把控制面改回 Next.js 全栈默认路径**（ADR 锁定 CSR SPA）
- ❌ **不能把侧栏 IA 改回「智能体市场」一级主路径**（数字伙伴为编排主入口）
- ❌ **不能让运行记忆不经审核直通权威知识**

### 3.2 React 18 —— 5 年锁定的 UI 框架

#### 选型理由

- 5 年生命周期已验证（React 16/2017 → 18/2022）
- 企业生态与 TypeScript 优先实践成熟
- 与 Vite CSR 控制面路径匹配

#### 与谁对比

| 框架 | 优点 | 缺点 | 我方考量 |
|---|---|---|---|
| **React 18 ✓** | 生态最大、TS 友好 | 学习曲线略陡 | **5 年首选 · 现仓已用** |
| Vue 3 | 国内友好 | 海外企业生态弱 | 国际版弱 |
| Svelte 5 | 性能好 | 企业案例少 | 风险 |
| Angular | 完整 | 重、人才稀缺 | 否决 |

#### 完成什么（功能映射 · v3.4 模块名）

| 模块 | React / 前端能力 |
|---|---|
| 全模块 M01–M15 | 组件渲染、懒加载路由、权限门禁 |
| 工作流程 M06 | React Flow DAG 编排 |
| 专家协作 M02 | 三栏布局、会话列表、消息上下文 Tab |
| 数字伙伴 M05 | 多 Tab 生命周期控制台 |
| 知识/技能/记忆/渠道/模型 | `de-employee-tabs` + KPI + 表格/卡片 |
| 平台设置 M12–M15 | 八 Tab 壳 + 嵌入治理页 |
| 向导 | `OnboardingGuide` 首次登录 v2 |

#### 故障案例 / 教训

- AngularJS → 2 不兼容、Vue 2→3 迁移成本高 → 选「大生态 + 小破坏性变更」
- Next.js 大版本 churn → **控制面锁定 Vite CSR**

### 5.3 Milvus 2.4 —— v3 重大变更：独立向量库

#### 选型理由（v3 关键）

- 独立部署，不与主库耦合：备份/复制风险小

|---|---|---|

| 最大规模 | 百万级 | **10 亿级** |
| 索引 | HNSW | HNSW / IVF / DiskANN / CAGRA |
| 备份 | 主库备份 | 独立备份 |
| 扩展 | 受 PG 限制 | 独立扩缩容 |
| 多租户 | Schema 隔离 | Partition + Database |
| 迁移成本 | — | 双写方案 → 切流量 |

#### 与谁对比（v3 关键）

| 方案 | 优点 | 缺点 | 我方考量 |
|---|---|---|---|
| **Milvus 2.4 ✓** | 亿级、丰富索引、独立部署 | 架构较重 | **首选** |
| pgvector | 与 PG 同一引擎 | 主库膨胀、100w+ 性能弱 | 取消 |
| Qdrant | Rust 写、性能好 | 2.0 后企业版划分 | 商业风险 |
| Weaviate | 模块多 | Hybrid Search 复杂 | 不适合 |
| Chroma | Python 原生 | 生产集群能力弱 | 不适合 |

#### 核心优势

  - Milvus Distributed（生产，亿级）
- 混合查询：向量 + BM25 + 元数据过滤
- Group/Partition：多租户隔离友好
- 可视化 Attu UI：运维友好

#### 完成什么

### 5.7 Apache Kafka 3.7+ —— 消息队列（v3.2 重大变更，原 NATS JetStream → Kafka）

#### 选型理由（v3.2 变更）

- **5 年企业级骨干**：Kafka 1.0 (2017) → 3.7 (2024)，10+ 年历史，业界标准
- **百万级/秒/集群吞吐量**：相比 NATS（5k/秒/节点）有 200x 提升
- **KRaft 共识**：3.3 起无 ZK 单点（KRaft = 内部 Raft 实现）
- **跨区复制（MirrorMaker 2）**：解决多区域消息同步问题
- **生态丰富**：Kafka Connect / Streams / ksqlDB / Schema Registry / Debezium CDC
- **国产替代成熟**：Apache RocketMQ 协议兼容；阿里云/腾讯云托管 Kafka

#### v3.2 关键决策：从 NATS JetStream 升级到 Kafka

| 维度 | NATS JetStream | Kafka |
|---|---|---|
| 单集群吞吐 | 5k/秒/节点 | **百万级/秒** |
| 部署 | 单二进制 | KRaft 集群（3 节点起）|
| 跨区复制 | 弱 | **MirrorMaker 2** |
| 持久化 | JetStream | KRaft + 多副本 |
| Schema 演进 | 无 | **Schema Registry** |
| CDC | 无 | **Debezium 集成** |
| 流处理 | 弱 | **Kafka Streams / ksqlDB** |
| 部署复杂度 | 极简 | 中（KRaft）|
| 退出成本 | 1 月 | 2-3 月 |

#### 与谁对比

| 方案 | 优点 | 缺点 | 我方考量 |
|---|---|---|---|
| **Kafka 3.7+ ✓** | 百万级吞吐、跨区复制、生态丰富 | 部署重、需 KRaft | **首选** |
| NATS JetStream | 部署极简、低延迟 | 5 年容量受限、跨区弱 | 不选 |
| RabbitMQ | 协议丰富 | 集群模式复杂、吞吐弱 | 不选 |
| Apache Pulsar | Kafka 兼容 | 学习曲线陡、社区小 | 备选 |
| 阿里云 RocketMQ | 托管、国产 | 锁定云 | 信创备选 |

#### 核心优势

- **百万级/秒/集群**：5 年路线图不需要再换
- **跨区复制原生支持**：MirrorMaker 2 是 Kafka 官方工具
- **Schema Registry**：自动管理 schema 演进
- **Kafka Connect 生态**：100+ 官方连接器（MySQL / Postgres / S3 / Elasticsearch）
- **Debezium CDC**：监听数据库变更做事件驱动
- **流处理**：Kafka Streams + ksqlDB 实时分析

#### 完成什么

| 模块 | Kafka 作用 |
|---|---|
| M06 工作流程 | Temporal Worker ↔ Python Task 异步事件 |
| M07 模型服务 | 异步调用事件流 |
| P10 渠道 | 推送队列 + 重试 + 死信 |
| M15 审计 | SignedLog 异步写入 |
| M08 文档 | Ingest 异步向量化（结合 Debezium CDC）|

#### 故障案例

- **NATS 集群瓶颈教训**：某团队 3 年后从 NATS 迁到 Kafka 经历 4 个月迁移 + 业务降级
- **RabbitMQ 集群配置教训**：2022 年某团队 RabbitMQ 集群脑裂，导致 30 分钟业务中断
- **结论**：从一开始就选 5 年可扩展的消息队列是经过验证的路径

### 9.2 gVisor —— Skill/MCP/Tool 沙箱

#### 选型理由

- 拦截 syscall：每个容器系统调用都经过 gVisor
- 比 Docker 安全：Docker 可被 escape（无 syscall 拦截）
- 比 Firecracker 易用：可与 Kubernetes 风格集成
- Google 主线：长期支持
- 5 年稳定

#### 故障案例

- **Docker 容器逃逸教训（2024）**：某 Kubernetes 集群因攻击者利用 runc 漏洞逃逸容器，导致节点被入侵
- **结论**：不可信代码必须用 gVisor 强制隔离（**不可替换**）

- **结论**：身份认证选 **"5 年 fork + 公司化运营"**

## 13. ADR 锁定决策（12 个）

### 13.1 ADR-001 to 005（v2 锁定）

| ADR | 锁死 |
|---|---|
| ADR-001 | Kubernetes（10 年） |
| ADR-002 | PostgreSQL 主库 |
| ADR-003 | gVisor 沙箱（不可替换） |
| ADR-004 | 等保 3 + ISO 27001 |
| ADR-005 | 多区域 cn-east + cn-south |

### 13.2 ADR-006: Go + Python 双栈（v3 强化）

**决策：** Go（业务）+ Python（AI Agent）双栈分工

**理由：**
- Go 性能 + 类型安全 + 部署简单 → 业务层首选
- Python 生态丰富 → AI 层首选
- 防止"Go 处理 AI 全部"或"Python 处理业务全部"的反模式
- 一套 protobuf IDL 同时生成 Go + Python SDK

**硬约束：**
- 业务逻辑禁用 Python
- AI 编排禁用 Go
- 通过 Connect-RPC 互通

### 13.3 ADR-007: Milvus 取代 pgvector（v3 重大变更）

详见 §5.3。

### 13.4 ADR-008: OpenSearch 取代 Elasticsearch（v3 重大变更）

详见 §5.4。

### 13.5 ADR-009: gRPC + Connect-RPC 协议统一

**决策：** Connect-RPC（gRPC + REST 双协议同一 IDL）

### 13.6 ADR-010: Apache Kafka 3.7+（v3.2 重大变更）

详见 §5.7。

**替代** 原 NATS JetStream 选型。

### 13.7 ADR-011: 控制面信息架构（v3.4）

**决策：** 侧栏锁定为 **协作 / 编排 / 能力** 三段 + 账号菜单（工作区 · 平台设置）；治理三项（访问控制 / 持续验证 / 审计中心）**聚合进平台设置八 Tab**，不再作为并列一级菜单无限膨胀。

**硬约束：**
- 不以「智能体市场」作为一级主路径
- 平台设置 Tab 顺序：`tenant | security | backup | apikeys | billing | access | zeroTrust | auditCenter`
- 首次登录向导与侧栏 IA 同构（能力接入 → 编排上岗 → 受控运营）

### 13.8 ADR-012: 数字伙伴引用已发布能力（v3.4）

**决策：** **岗位数字伙伴**为编排主入口；模型 / 知识 / 技能 / 记忆 / 渠道分控制面发布后，数字伙伴**只引用已发布版本**；记忆中心产出**知识候选**，不经审核不得直通权威知识。

**硬约束：**
- 运行记忆 ≠ 权威知识
- 工作流可发布为技能，再被数字伙伴装配
- 底层 Agent 为执行内核，不回退为侧栏主卖点

## 22. ADR 流程

任何组件更换必须通过 ADR 流程：

```
1. 业务方提变更
   ↓
2. 架构评审（架构师 + 安全 + 合规）
   ↓
3. ADR 起草（用 doc/ADR-000-template.md 模板）
   ↓
4. 影响评估（5 年路线、退出成本）
   ↓
5. CTO 拍板
   ↓
6. 更新本规范文档
   ↓
7. CI/CD 同步更新 Helm Chart
```

**关键：** 不允许"先用了再说"。任何"以后再优化"的提议都要走 ADR。
